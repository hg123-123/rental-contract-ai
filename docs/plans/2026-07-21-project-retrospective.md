# 项目复盘：合同审查AI助手

## 项目概述

**一句话**：帮大学生看懂租房合同和劳动合同的AI工具，基于RAG知识库检索增强生成，避免模型幻觉。

**时间线**：2026年7月17日 → 7月21日（5天）

**当前状态**：MVP已上线，基于Dify聊天助手 + Cloudflare Tunnel，待推广验证。

---

## 关键决策记录

### 决策1：微信小程序 vs H5 vs Dify原生

| 选项 | 结果 |
|---|---|
| 微信小程序 | ❌ 法律服务类目需机构资质，个人无法通过审核 |
| H5自建前端 | ⚠️ 做出来了但部署被墙（Vercel/GitHub Pages不稳定） |
| **Dify原生聊天页面** | ✅ 零前端、零部署、多轮记忆原生支持 |

**教训**：MVP阶段先问"能不能不写代码"。Dify自带的聊天界面完全满足验证需求，自建前端花了大量时间解决部署问题，最终没用上。

### 决策2：Embedding模型选型

| 尝试 | 结果 |
|---|---|
| bge-large-zh-law（Ollama本地） | ❌ 不在Ollama上 |
| nomic-embed-text（Ollama本地） | ❌ 英文模型，中文法律检索完全不准 |
| shaw/dmeta-embedding-zh（Ollama本地） | ❌ Ollama 0.5.7不支持BERT架构 |
| qwen3-embedding（Ollama本地） | ❌ 需要更新版Ollama，网络下载被墙 |
| **通义千问 text-embedding-v3（云端API）** | ✅ 中文效果好，免费额度够用 |

**教训**：本地部署嵌入模型坑多（版本兼容、网络限制、模型质量），云API几分钟搞定。MVP阶段优先用云服务。

### 决策3：聊天助手 vs Chatflow

| 尝试 | 结果 |
|---|---|
| **聊天助手** | ✅ 稳定，原生多轮记忆，发布即有公开链接 |
| Chatflow | ❌ 一直400 Bad Request，配置复杂，多轮对话有Bug |

**教训**：Dify 1.16是RC版本，Chatflow不够稳定。聊天助手足够MVP使用。

### 决策4：知识库策略

最初计划通过爬虫批量导入法律条文，但最终采用**手工精选+格式化的方式**，每条法条标注同义词/口语别名。这个决策被验证是正确的——检索命中率显著提升。

### 决策5：RAG vs 纯Prompt

设计阶段就确定用RAG而非依赖模型自身能力，事后证明这个决策是产品准确性的底线。没有知识库支撑时，DeepSeek-V4-Pro会编造法条编号。

## 做对的事

1. **RAG架构选型**：法条原文锁定在知识库，LLM只负责解释，从架构上防幻觉
2. **风险知识库手工填充**：30+风险点来自真实经验，这是产品护城河
3. **措辞红线设计**：禁用"违法/霸王条款"，用"建议关注/值得注意"，合规可控
4. **先聚焦杭州**：有一份真实合同做测试基准，不是泛泛而谈
5. **快速放弃不work的方案**：微信小程序、Vercel、Chatflow都是半天内试过→放弃

## 做错的事

1. **过早投入前端开发**：花了两天写React对话页面，最终没用上
2. **在嵌入模型上纠结太久**：试了5种本地方案失败后才转向云API
3. **Tunnel稳定性被低估**：每次笔记本休眠Tunnel就断，MVP体验受影响
4. **缺乏真实用户反馈**：还没找任何一个同学实际用过

## 如果要重来一次

1. **第1天**：Dify建聊天助手 + 通义千问API + 手写5个核心法条 → 立刻能用
2. **第2天**：补齐知识库 + 找5个同学测试
3. **第3天**：根据反馈迭代提示词和知识库
4. **不做**：前端开发、本地嵌入模型、Chatflow、GitHub Pages部署
